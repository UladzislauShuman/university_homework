## Где что работает

| Что | Где | Ресурсы |
|---|---|---|
| сервис (Spring Boot) | на компе, порт 8080 | JVM 1 ГБ |
| JMeter | на компе | JVM 1 ГБ |
| Postgres 17 | Docker, порт 5432 | 1 CPU, 1 ГБ |
| Redis 8 | Docker, порт 6379 | 0.5 CPU, 256 МБ |
| Prometheus | Docker, http://localhost:9090 | 0.5 CPU |
| Grafana | Docker, http://localhost:3000, дашборд «lab2 — кэширование» | 0.5 CPU |

Сервис и JMeter запускаются не в Docker, как советовал преподаватель: так меньше лишних накладных расходов на сеть.

## Запуск

```bash
cd ASS/lab2/code
docker compose up -d                                   # база, кэш, мониторинг
(cd app && ./mvnw -q -DskipTests package)              # собрать сервис (нужна JDK 21+)
brew install jmeter                                    # один раз

python3 scripts/analyze.py                             # таблица + графики в ../ответ/фото
```

```bash
docker compose down -v
docker image prune -f
```

## JMeter: как им пользоваться

JMeter — это Java-программа. Она запускает много потоков (**виртуальных пользователей**), и каждый шлёт запросы по сценарию из файла `.jmx` (это XML).

**1. Посмотреть или поменять сценарий в окне программы:**

```bash
jmeter -t jmeter/users.jmx
```

Слева дерево сценария:
- **Test Plan** — корень. В нём переменные `host`, `port`, `maxId`.
- **Thread Group «users»** — сколько пользователей (`threads`), за сколько секунд они все стартуют (`rampup`) и сколько длится тест (`duration`). Значения заданы как `${__P(threads,200)}`: «взять из параметра `threads`, а если его нет — 200».
- **HTTP Request «GET /users/{id}»** — сам запрос. Путь `/users/${__Random(1,${maxId})}`: каждый раз берётся случайный id.
- **Summary Report** — таблица результатов. Видна, если запускать тест прямо в окне (зелёная кнопка ▶).

В окне удобно отлаживать сценарий на паре пользователей. **Настоящую нагрузку в окне не запускают**: интерфейс сам съедает много CPU и искажает результат.

**2. Нагрузка в консольном режиме (так и делается в лабе):**

```bash
jmeter -n -t jmeter/users.jmx -q jmeter/lab2.properties \
       -Jthreads=200 -Jrampup=30 -Jduration=600 \
       -l results/my.jtl
```

- `-n` — без окна;
- `-t` — файл сценария;
- `-q` — дополнительный файл настроек;
- `-J имя=значение` — параметр, который сценарий читает через `__P`;
- `-l` — куда писать результат каждого запроса (CSV: время, длительность, код ответа...).

Каждые 10 секунд в консоль печатается сводка: `summary = 1091213 in 00:01:00 = 18172.3/s Avg: 10 Min: 0 Max: 172 Err: 0 (0.00%)`. Это значит: запросов всего, за сколько времени, запросов в секунду, средняя / минимальная / максимальная задержка в мс, ошибки.

**3. HTML-отчёт по готовому результату:**

```bash
jmeter -g results/my.jtl -q jmeter/lab2.properties -o results/my-report
open results/my-report/index.html
```

Там сводная таблица (перцентили 90/95/99) и графики. Самые полезные — «Response Times Over Time», «Response Time Percentiles» и «Transactions Per Second» (на вкладке Charts).

**Важно про модель нагрузки.** Обычная Thread Group — это «закрытая» модель. Каждый из 200 пользователей ждёт ответ и только потом шлёт следующий запрос. Если сервис тормозит, нагрузка сама уменьшается: пользователи реже отправляют запросы. В реальности клиенты приходят независимо от того, тормозит ли сервис («открытая» модель). Поэтому закрытая модель **смягчает** картину деградации. Об этом надо помнить при чтении результатов пятого задания.
